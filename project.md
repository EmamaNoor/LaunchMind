# LaunchMind

A multi-agent system that autonomously runs a micro-startup. You give it a startup idea, and a team of collaborating AI agents handles everything from product definition to code generation, marketing copy, GitHub PRs, Slack posts, and email outreach. No human in the loop after the initial idea.

## What This Project Does

LaunchMind takes a plain-text startup idea as input and produces real-world outputs through a network of autonomous, LLM-powered agents. These agents reason independently, communicate through structured JSON messages, and take actions on real platforms.

The agents don't print results to a terminal and call it a day. They take actual actions:
- Open real GitHub pull requests with generated code
- Post formatted messages to a real Slack workspace
- Send real emails through SendGrid

This is not a chatbot or a linear pipeline. It's a system where agents make decisions, review each other's work, and request revisions when outputs aren't good enough.

## Architecture

### Agent Overview

The system has five agents, each with a defined role, inputs, and outputs.

**CEO Agent (Orchestrator)**
The brain of the system. Receives the startup idea and coordinates everything.

Responsibilities:
- Receive the startup idea as plain text
- Use an LLM to break the idea into structured tasks, one per agent
- Send each task as a structured JSON message to the correct agent
- Wait for responses from each agent
- Review responses using LLM reasoning (not just forwarding, actually evaluating quality)
- Send revision requests if an agent's output is poor or incomplete
- Compile a final summary and post it to the Slack channel
- Log every decision it made and why

Constraints:
- Tasks must be generated by the LLM based on the idea, not hardcoded
- The review step cannot be skipped. Passing output from Agent A to Agent B without evaluating it is piping, not orchestration.

LLM usage (minimum two calls):
1. Decompose the startup idea into agent tasks
2. Review each agent's output and decide if it's acceptable or needs revision

**Product Agent**
Thinks like a product manager. Takes the CEO's task and produces a structured product spec.

Responsibilities:
- Receive a task message from the CEO containing the startup idea and focus areas
- Use an LLM to generate a product specification
- Send the spec as structured JSON to both the Engineer and Marketing agents
- Send a confirmation message back to the CEO

Product spec JSON schema:

| Field              | Type   | Description                                                    |
|--------------------|--------|----------------------------------------------------------------|
| value_proposition  | string | One sentence: what the product does and for whom               |
| personas           | array  | Each persona has: name, role, and pain_point                   |
| features           | array  | Each feature has: name, description, and priority (1=highest)  |
| user_stories       | array  | Three stories in "As a / I want / So that" format              |

**Engineer Agent**
The builder. Reads the product spec and produces real, runnable code with real GitHub actions.

Responsibilities:
- Receive the product spec from the Product agent
- Use an LLM to generate a complete, working HTML landing page (headline, subheadline, features section, CTA button, CSS styling)
- Create a GitHub issue titled "Initial landing page" with an LLM-generated description
- Commit the HTML file to a new branch
- Open a pull request with an LLM-generated title and body
- Send the PR URL and issue URL back to the CEO as structured JSON

GitHub requirements:
- Public repository
- Authenticate with a GitHub PAT stored as an environment variable (never hardcoded)
- Commit authored by the agent (e.g., "EngineerAgent <agent@launchmind.ai>")
- The PR must be visible in the repo

**Marketing Agent**
Thinks like a growth marketer. Reads the product spec and produces real marketing outputs.

Responsibilities:
- Receive the product spec from the Product agent
- Use an LLM to generate: a tagline (under 10 words), a short product description (2-3 sentences), a cold outreach email to a potential user or investor, and three social media post drafts (Twitter/X, LinkedIn, Instagram)
- Send the cold outreach email to a test address using SendGrid
- Post a Slack message to a designated channel with the tagline, one-line description, and a link to the GitHub PR (must use Slack Block Kit formatting)
- Send all generated copy back to the CEO as structured JSON

**QA / Reviewer Agent**
Reviews the Engineer's code and the Marketing agent's copy for quality and consistency.

Responsibilities:
- Receive the Engineer's HTML output and the Marketing agent's copy from the CEO
- Use an LLM to review the landing page (does it match the product spec? is the headline consistent with the value proposition? are features mentioned?)
- Use an LLM to review marketing copy (is the tagline compelling? does the cold email have a clear CTA? is the tone right?)
- Post review comments on the GitHub PR using the GitHub API (at least two inline comments on the HTML file)
- Send a structured review report back to the CEO with a pass/fail verdict and a list of specific issues
- If the verdict is "fail", the CEO instructs the relevant agent to revise, creating a dynamic feedback loop

## Agent Communication Protocol

### Message Schema

Every message between agents is a JSON object with these fields:

| Field              | Type   | Required | Description                                                    |
|--------------------|--------|----------|----------------------------------------------------------------|
| message_id         | string | Yes      | Unique ID (e.g., UUID)                                         |
| from_agent         | string | Yes      | Name of the sender (e.g., "ceo", "product", "engineer")       |
| to_agent           | string | Yes      | Name of the receiver                                           |
| message_type       | string | Yes      | One of: "task", "result", "revision_request", "confirmation"   |
| payload            | object | Yes      | The actual content (varies per message type)                   |
| timestamp          | string | Yes      | ISO 8601 timestamp                                             |
| parent_message_id  | string | No       | ID of the message this responds to (for traceability)          |

Example task message from CEO to Product agent:

```json
{
  "message_id": "msg-001",
  "from_agent": "ceo",
  "to_agent": "product",
  "message_type": "task",
  "payload": {
    "idea": "A platform where students list second-hand textbooks for sale",
    "focus": "Define the core user personas and top 5 features"
  },
  "timestamp": "2025-10-01T09:00:00Z"
}
```

### Message Bus Options

Option A: Shared Python dictionary or JSON file (simplest). All agents run in the same process. A shared `message_bus` dictionary routes messages. Agent A appends to `message_bus['agent_b']`, and Agent B reads from it.

Option B: SQLite database (intermediate). Agents write to a `messages` table. Each agent polls for new messages addressed to it. Works well for separate threads or processes.

Option C: Redis pub/sub (advanced). Each agent subscribes to a channel named after itself. Messages are published to the recipient's channel. This is how production MAS systems work.

Whichever approach you pick, the full message history must be inspectable at any time.

### Dynamic Decision-Making (Required)

The system must have at least one feedback loop: the CEO receives a response from another agent, reasons about it using an LLM, and changes its next action based on that reasoning.

Minimum version: CEO receives the Product agent's spec, sends it to the LLM with a review prompt ("Is this specific enough? What's missing?"), and if the LLM flags problems, sends a `revision_request` back to the Product agent with specific feedback.

Stronger version: QA agent reviews the Engineer's HTML and returns a "fail" verdict. The CEO reasons about it and instructs the Engineer to revise, addressing the specific issues raised.

If agents run in a fixed sequence with no feedback loops, the system is a pipeline, not a multi-agent system.

## Platform Setup

### GitHub
1. Create a public repo named `launchmind`
2. Go to Settings > Developer Settings > Personal Access Tokens > Tokens (classic)
3. Generate a token with permissions: `repo` (full control), `workflow`
4. Store as env var: `GITHUB_TOKEN=your_token_here`
5. Never commit the token. Use `.env` + `.gitignore`
6. Test: `curl -H 'Authorization: token $GITHUB_TOKEN' https://api.github.com/user`

### Slack
1. Go to api.slack.com/apps, click "Create New App" > "From scratch"
2. Name it "LaunchMind Bot", select your workspace
3. In "OAuth & Permissions", add Bot Token Scopes: `chat:write`, `channels:read`, `channels:join`
4. Install to Workspace, copy the Bot User OAuth Token (starts with `xoxb-`)
5. Store as env var: `SLACK_BOT_TOKEN=xoxb-your-token`
6. Create a `#launches` channel and invite the bot with `/invite @LaunchMindBot`

### SendGrid (Email)
1. Create a free SendGrid account (100 emails/day, no credit card)
2. Settings > API Keys > create key with "Mail Send" permission
3. Store as env var: `SENDGRID_API_KEY=SG.your_key_here`
4. Settings > Sender Authentication > verify your sender email address
5. Test with a quick script before integrating into the agent

## Code Patterns

### GitHub API (Engineer Agent)

```python
import requests, os, base64

GITHUB_TOKEN = os.environ["GITHUB_TOKEN"]
REPO = "yourusername/launchmind"
HEADERS = {
    "Authorization": f"token {GITHUB_TOKEN}",
    "Accept": "application/vnd.github+json"
}

# 1. Create a branch
requests.post(
    f"https://api.github.com/repos/{REPO}/git/refs",
    headers=HEADERS,
    json={"ref": "refs/heads/agent-landing-page", "sha": "<base_sha>"}
)

# 2. Commit a file
content = base64.b64encode(html_content.encode()).decode()
requests.put(
    f"https://api.github.com/repos/{REPO}/contents/index.html",
    headers=HEADERS,
    json={
        "message": "Add landing page",
        "content": content,
        "branch": "agent-landing-page"
    }
)

# 3. Open PR
r = requests.post(
    f"https://api.github.com/repos/{REPO}/pulls",
    headers=HEADERS,
    json={
        "title": "Initial landing page",
        "body": pr_body,
        "head": "agent-landing-page",
        "base": "main"
    }
)
pr_url = r.json()["html_url"]
```

### Slack with Block Kit (Marketing Agent)

```python
import requests, os

def post_to_slack(tagline, description, pr_url):
    payload = {
        "channel": "#launches",
        "blocks": [
            {
                "type": "header",
                "text": {"type": "plain_text", "text": "New Launch: " + tagline}
            },
            {
                "type": "section",
                "text": {"type": "mrkdwn", "text": description}
            },
            {
                "type": "section",
                "fields": [
                    {"type": "mrkdwn", "text": f"*GitHub PR:* <{pr_url}|View PR>"},
                    {"type": "mrkdwn", "text": "*Status:* Ready for review"}
                ]
            }
        ]
    }
    requests.post(
        "https://slack.com/api/chat.postMessage",
        headers={"Authorization": f"Bearer {os.environ['SLACK_BOT_TOKEN']}"},
        json=payload
    )
```

### SendGrid Email (Marketing Agent)

```python
from sendgrid import SendGridAPIClient
from sendgrid.helpers.mail import Mail
import os

def send_email(subject, body, to_email):
    message = Mail(
        from_email="verified@yourdomain.com",
        to_emails=to_email,
        subject=subject,
        html_content=f"<p>{body}</p>"
    )
    sg = SendGridAPIClient(os.environ["SENDGRID_API_KEY"])
    sg.send(message)
```

### Calling an LLM Inside an Agent

```python
import anthropic, os

client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

def call_llm(system_prompt, user_prompt):
    response = client.messages.create(
        model="claude-sonnet-4-20250514",
        max_tokens=1000,
        system=system_prompt,
        messages=[{"role": "user", "content": user_prompt}]
    )
    return response.content[0].text
```

## Error Handling

- Catch LLM refusals or timeouts. Log the error and have the agent either retry with a revised prompt or report the failure to the CEO.
- A system that crashes when an API misbehaves is not production-ready. Wrap all external API calls in try/except blocks.
- The CEO agent should be able to handle partial failures and still produce a summary of what succeeded and what didn't.
